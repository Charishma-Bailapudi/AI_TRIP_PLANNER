# Coding Instructions & Standards - AI Trip Planner

This document serves as the guide for all developers contributing code to this repository. All contributions must adhere to these guidelines to ensure code quality, security, performance, and scalability.

---

## 1. Architecture Rules

We enforce **Clean Architecture** to maintain clear segregation of concerns and high testability.

### 1.1. Architectural Layers
*   **Presentation Layer:** React components, templates, styles, and UI state managers. **Business logic must not exist inside React components.** Components only render state and trigger events.
*   **Application Layer:** Services that contain application-specific business logic, coordinate workflow, and handle interactions between domain entities.
*   **Domain Layer:** Core enterprise business rules, entities, models, and repository interfaces. Clean of framework dependencies.
*   **Infrastructure Layer:** Repositories, Express Router config, Database controllers, Mongoose models, external API clients, and auth providers.

### 1.2. Coding Rules
*   **Thin Controllers:** Controllers must only handle parsing request inputs, delegating tasks to services, and returning structured API responses.
*   **Thick Services:** Services must contain the core business logic, calculations, and orchestrations.
*   **Isolated Database Access:** Direct database queries (Mongoose) are prohibited in services/controllers. Database access must be isolated through **Repositories**.

---

## 2. Frontend Rules

### 2.1. Frontend Stack
*   **Framework:** React.js
*   **Type Safety:** TypeScript
*   **Styling:** Tailwind CSS
*   **State & Cache:** React Query (for server state/caching)
*   **Routing:** React Router
*   **Local State Context:** Context API

### 2.2. Development Standards
*   **Functional Components Only:** Class components are forbidden. Use pure functional components with Hooks.
*   **Hook Patterns:** All side-effects and API mutations must reside in custom hooks.
*   **Reusable UI Components:** Build atomic, highly styled, reusable UI components (e.g. `Button.tsx`, `Modal.tsx`) matching design tokens.
*   **Mobile-First Design:** Write utility classes starting with mobile layouts and use screen size prefixes (`md:`, `lg:`) for larger resolutions.
*   **Dark Mode Support:** Implement a dark-mode-first styling architecture.
*   **Loading States:** Provide visual skeleton loaders, progress bars, or spinner overlays for *every* asynchronous API call.
*   **Error Boundaries:** Wrap component trees in Error Boundaries to prevent total app crashes when local rendering errors occur.

---

## 3. Backend Rules

### 3.1. Backend Stack
*   **Runtime:** Node.js
*   **Framework:** Express.js
*   **Type Safety:** TypeScript
*   **Database ORM:** MongoDB & Mongoose

### 3.2. Development Standards
*   **Feature-Based Structure:** Code must be organized in folders grouped by feature domain.
*   **Strict Validation:** Validate all incoming HTTP payloads (query params, path params, request bodies) at the routing boundary using validation libraries (e.g. Zod or Joi).
*   **Global Error Handling:** Use custom exception middleware to capture errors. All route endpoints must catch errors and pipe them to a centralized error handling middleware.
*   **Pure Asynchronous Code:** Use `async/await` exclusively. Callback-based code or raw `.then()` chaining is forbidden.
*   **Secure Secrets:** Database URIs, passwords, private keys, and API tokens must reside in environment variables and never be committed to source control.

## 4. AI Agent Rules

Our application is built on a multi-agent system. The AI engine is divided into 7 specialized subagents:
1.  **Orchestrator Agent:** Receives user prompts, directs task pipelines, and aggregates final results.
2.  **Segment Builder Agent:** Parses destination arrays into chronological segments.
3.  **Flight Search Agent:** Queries flights database/API and optimizes travel windows.
4.  **Train Search Agent:** Looks up railway routes, departures, and schedules.
5.  **Connectivity Agent:** Addresses travel legs for destinations without direct airport/railway connections.
6.  **Budget Agent:** Tracks cost ceilings, handles conversions, and manages budget tier rules.
7.  **Itinerary Agent:** Compiles sightseeing places, dining spots, and daily timing breakdowns.

### 4.1. Agent Constraints
Every agent must adhere to the following output constraints:
*   **Clear Responsibility:** Must operate only within its designated scope.
*   **Structured JSON Output:** Must output structured JSON conforming to preset schemas. Free-form text responses are forbidden.
*   **Confidence Score:** Must return a float value between `0.0` and `1.0` indicating the confidence level of the generated data.
*   **Explanation:** Must include a clear, user-friendly natural-language reason/rationale for the decisions made.

---

## 5. Transport Analysis Rules

For every segment (Source → Destination), the system must execute:
1.  **Flight Search:** Check flight routes between nearest commercial airports.
2.  **Train Search:** Check railway schedules and connections.
3.  **Nearby Airport Search:** Identify nearby commercial airports if target city lacks an airport.
4.  **Nearby Railway Station Search:** Identify nearby train stations if target city lacks a railway station.

### 5.1. Non-Direct Connectivity Strategy
If direct connectivity is unavailable, the **Connectivity Agent** must:
*   Find the nearest major airport and railway station.
*   Suggest local taxi routes and fares.
*   Suggest local bus services and timetables.
*   Suggest alternate multi-modal transit routes.

### 5.2. Output Metrics
Every transport suggestion must return:
*   **Cost:** Estimated price in the selected currency.
*   **Duration:** Estimated transit time in minutes.
*   **Recommendation Reason:** Natural language rationale (e.g., "Saves 4 hours, fits within moderate budget").

## 6. API Design Rules

### 6.1. REST Standards
Apply semantic HTTP methods:
*   `GET`: Retrieve resources.
*   `POST`: Create new resources or execute heavy operations (e.g., trip analysis).
*   `PUT`: Update existing resources.
*   `DELETE`: Remove resources.

### 6.2. Unified Response Format
All API responses must match this structure:
```json
{
  "success": true,
  "data": {},
  "message": "Operation completed successfully",
  "errors": []
}
```

---

## 7. MongoDB Rules

### 7.1. Database Collections
1.  **Users:** User profile data, password hashes, registration details.
2.  **Trips:** Main trip information (origin, overall metadata, date constraints).
3.  **TripSegments:** Extracted multi-city segments.
4.  **TransportOptions:** Evaluated transit plans per segment.
5.  **ConnectivityAnalysis:** Last-mile transfer information.
6.  **Itineraries:** Day-by-day scheduled activities.
7.  **CachedRoutes:** Saved route and transit searches keyed by hashes.

### 7.2. Requirements
*   **Indexes:** Add indexes on frequently queried fields (e.g., `userId`, `tripId`, `cacheKey`).
*   **Timestamps:** Enable Mongoose schema options `{ timestamps: true }` on all collections.
*   **Soft Delete Support:** Implement soft deletes (e.g. `deletedAt` field and Query middleware) for `Trips` and `Users`.
*   **GeoSpatial Indexes:** Apply `2dsphere` geospatial indexing on location/coordinate fields to run proximity queries.

---

## 8. External API Rules

Our system integrates with the **Gemini API**, **Flight API** (Amadeus/Skyscanner), **Railway API** (Rome2Rio), and **Mapbox API**.

*   **Retry Logic:** Automatically retry failed network requests up to 3 times with exponential backoff.
*   **Caching:** Cache slow external responses (e.g. flights/train lookup) to database or Redis caching layers.
*   **Circuit Breaker Pattern:** Temporarily disable external API routes if failure rates cross a 50% threshold within a 5-minute window to avoid server lockups.
*   **Timeout Handling:** Set strict timeout limits (e.g., 5 seconds for maps, 10 seconds for flights/trains) to prevent hanging connections.

---

## 9. Offline Support Rules

To ensure usability while traveling:
*   **IndexedDB Cache:** Cache active itineraries and map coordinates locally in the user's browser using IndexedDB.
*   **Online Synchronization:** Queue modifications offline and sync updates to the backend database as soon as connection is restored.
*   **Offline Viewing:** Enable users to view saved itineraries in read-only mode without internet access.
*   **Offline PDF:** Ensure PDF versions of travel plans are downloaded and accessible locally.

---

## 10. Testing Rules

A robust test suite is required. All pull requests must meet a **minimum code coverage of 80%**.

*   **Backend Testing:**
    *   *Unit Tests:* Mock repository calls and test controllers/services isolation.
    *   *Integration Tests:* Spin up testing databases to test complete API endpoints (e.g. Supertest).
*   **Frontend Testing:**
    *   *Component Tests:* Verify UI elements render and handle events as expected (React Testing Library).
    *   *Hook Tests:* Test custom state hooks and server integration mocks.

---

## 11. Security Rules

*   **JWT Authentication:** Authenticate users using JSON Web Tokens.
*   **Refresh Token Rotation:** Access tokens must expire quickly (e.g., 15 minutes). Use HTTP-only cookies to securely store and rotate Refresh Tokens.
*   **Rate Limiting:** Protect endpoints against brute-force attacks and scrape attempts using API rate limiters.
*   **Helmet:** Secure HTTP headers using Helmet middleware.
*   **CORS:** Apply strict Cross-Origin Resource Sharing rules.
*   **Input Sanitization:** Sanitize user input prior to database storage to protect against XSS and MongoDB Injection attacks.
*   **Password Hashing:** Always hash passwords using `bcrypt` before storing.

---

## 12. UI/UX Rules

Aesthetics are vital to the user experience.
*   **Dark Mode First:** Visual theme designed around deep neutral/slate backgrounds and glowing visual highlights.
*   **Glassmorphism:** Use translucent card layouts (`backdrop-filter: blur()`) with high-contrast thin borders.
*   **Animations:** Smooth state changes using **Framer Motion** or CSS transitions (avoid sudden page snaps).
*   **Consistent Spacing:** Follow a 4px/8px grid system for margins, padding, and layout grids.
*   **Device Priority:**
    1.  Mobile (primary focus for travelers on the go)
    2.  Tablet
    3.  Desktop

---

## 13. Code Generation Rule

When generating code files (or updates) as a developer or agent:
1.  **Generate Complete Files:** Do not use ellipses (`...`) or skip unchanged code blocks. Write out the entire file structure.
2.  **No Placeholders:** Avoid adding placeholders, todo items, or stub code.
3.  **No Mock Implementations:** Avoid mock setups unless explicitly requested by the user.
4.  **Include Imports:** Include all necessary external and relative imports.
5.  **Include Types/Interfaces:** Ensure all components, functions, parameters, and payloads are explicitly typed.
6.  **Include Validation:** Add schema/input validation where input parameters enter modules.
7.  **Follow Project Structure:** Respect the feature-based directory organization.
8.  **Ensure Production-Ready Code:** All code generated must compile cleanly, run without lint warnings, and be deployable.
